## New or newly concrete issues

### A11 — Major implementation gate: hashes do not enforce actual response alignment or arm integrity

**Evidence/location:** `paired_evaluation.py::evaluate` accepts three positional outcome arrays and one caller-supplied row-ID list. It checks that those IDs are unique and have the right length, but receives no per-arm row/request IDs to join or compare. `render.py::plan` deliberately randomizes request order, so a future collector must map responses back to numeric source/profile order. It checks equal arm populations but does not independently enforce that N has no facts or F-I omits income if an input file is corrupted. `messages()` accepts all whitelisted fact keys regardless of arm.

**Consequence:** Correct dimensions, a fixed X hash, and a shared row-ID hash can coexist with a wrong model contrast or wrong treatment. In my synthetic check, copied human outcomes gave zero signed error; reordering only one arm's first eight values produced **800 CAD signed error while both reported hashes remained unchanged**. This is not proof of a current collection error—there is no runner—but demonstrates that the advertised linkage guarantee stops before actual responses.

**Proposed fix:** Add a keyed collection/assembly boundary using immutable request IDs, arm, source/profile IDs, prompt hash, and attempt status. Join each response to the frozen design and reject unexpected, duplicated or unaccounted requests. Enforce arm-specific fact restrictions again at the transmission boundary; do not rely only on prior file generation. Keep invalid/transport-exhausted requests as explicit planned rows.

**Verification criterion:** Shuffling arrival order leaves evaluation unchanged after keyed joining. A one-arm ID/value mismatch, duplicate request, missing planned record, or income field injected into F-I is rejected before scoring/transmission. Exercise these checks through a simulated runner replay, not just directly supplied arrays.

### A12 — Moderate presentation issue: two recipients can receive the same complete canonical name

**Evidence/location:** `render.py::NAME` has one name per gender/ethnicity cell and `profile_text()` chooses solely from that cell. `tests/test_render.py::setUp` itself creates a pair with the same name and different incomes. My in-memory check rendered two “Matthew Smith” recipients with 30k and 120k incomes. No frequency in actual source pairs can be inferred without the data.

**Consequence:** The reconstruction can introduce an identity ambiguity or apparent biographical inconsistency. Person A/B labels may mitigate it, but the packet has no evidence that this feature is harmless. It could interact with paired comparison or income information. This is a concrete part of A4, not a claim that all observed discrepancies would be caused by names.

**Proposed fix:** Audit and report name collisions. Use a documented deterministic pair-distinct mapping from the permitted name pool where available, or otherwise explicitly establish that A and B are distinct hypothetical people. Include collision handling in the planned presentation comparison; do not silently change it after seeing model outcomes.

**Verification criterion:** Publish the frozen rule, a synthetic same-cell example, actual collision counts when authorized source data are available, and the predeclared handling. Presentation-robust claims require supporting model evidence, not the existence of the rule alone.

### A13 — Moderate protocol gap: the common-task audit has a request grid but no frozen analysis target

**Evidence/location:** `protocol.md:151–157`; `render.py::common_task_plan`. The code generates six cells per base, always changing the first recipient and leaving the companion fixed. It does not define the focal-outcome summary, equal-base weighting, failed-cell treatment, or whether the conclusion is specific to focal position A. Base contexts are sampled from pilot records and can share a person; they are not 16 independent humans.

**Consequence:** The grid is a valid model-only diagnostic design, but an after-the-fact choice of which answer, interaction or average to emphasize could reproduce the selection problem it is intended to diagnose. A nonzero result here is input sensitivity, not matched human fidelity. One recorded answer per cell also does not distinguish stable sensitivity from generation noise.

**Proposed fix:** Predeclare, for example, an equal-base mean of the focal-A difference-in-differences: mean_b[(Y_low,30 − Y_low,120) − (Y_high,30 − Y_high,120)]. Specify the omitted-income summaries separately, completeness/bounding rules, and any repeat allocation. Either counterbalance focal position as part of the presentation plan or explicitly restrict this diagnostic to focal A. Preserve the fact that no human outcomes validate these counterfactual biographies.

**Verification criterion:** A self-contained audit analysis specification identifies every cell used and its weight before responses exist. Artificial additive and interacting response tables produce their known summaries, and incomplete cells lead to the declared bounds or an explicit incomplete diagnostic rather than selective deletion.

## Collection decision and smallest next step

The revised target makes continuous descriptive scoring coherent without a bootstrap CI or a policy threshold. I would not require those abandoned inferential objects to approve an implementation. I would require the following before main collection:

1. Freeze the exact cohort/prefix, model/settings, transmitted messages, budget, transport/invalid policy, run order, repeats if any, and the analyses of the two small diagnostic audits. Verify the source-to-prompt fact crosswalk, including the renderer's numerical income thresholds and biographical expansions; those semantics cannot be independently checked from this packet alone.
2. Implement the isolated runner and keyed assembly checks in A11, including logged model identity, actual messages, all attempts, outcomes and cost. Show a synthetic replay covering randomized arrival, failures and resume without duplicate scoring. Separately demonstrate that the reference outcome store is unavailable to generation.
3. Complete a bounded engineering pilot and freeze any changes before main outputs. Use both validity and contrast-weight exposure to plan what can be learned. The receipt reports single-arm completion widths of about **193 CAD for its 1% random-failure scenario and 420 CAD for its 1% highest-leverage scenario**; at about 5%, approximately **868/1,864 CAD**. These are supplied design scenarios, not probabilities, observed model failures, or uncertainty intervals. A nominal 95% valid-output rule alone would not establish useful subgroup identification.

Substantive margins are required only if categorical scientific or policy-fidelity claims are restored. Repeated-generation evidence is required for stability/expectation claims, and executed presentation checks for presentation-robust claims. Neither can be replaced by exact finite arithmetic. A finite one-rollout report can instead remain descriptive and explicitly conditional, but its importance is an empirical question.

**Recommended core remains Study1, N/F/F-I, one primary contrast, continuous signed and absolute-error changes, the small common-task diagnostic, and a prespecified presentation audit.** Defer Study2 and additional machinery. The smallest result that would strengthen the methods case is a transparent realized discrepancy or loss change, bounded where necessary, that reveals something aggregate checks miss and whose limits are tested by those targeted diagnostics. A precise finite null/mixed score should also be reported; no desired sign is a condition for proceeding. Broader human mechanisms, national-population fidelity and system-level political simulation remain outside the design.
