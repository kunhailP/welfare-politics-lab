## Remaining and new findings

### B10 — New, moderate implementation gap: the planner does not enforce the actual arm ablation

**Evidence/location.** `render.py:99–103` verifies equal sets of agent IDs and selects the high/low cohort from F. At `118` it independently renders whatever facts each arm file supplies. It does not check N has no facts, F-I equals F with only income removed, or employment/parenthood match across F and F-I. Dictionary construction also silently collapses duplicate agent records. The renderer unit test verifies a manually constructed good F/F-I pair; it does not establish those properties for every planned record. I changed N input records in the supplied synthetic fixture to include household income: `plan()` accepted them and emitted income-bearing N messages.

**Consequence.** The current preparation function creates the intended files, so this is not evidence of a contaminated real campaign. Nevertheless, the advertised information-only manipulation is not an invariant enforced at the collection boundary. A stale, edited or incorrectly joined bundle can silently change the intervention while retaining the original arm labels.

**Concrete fix.** Validate arm-file uniqueness and the complete relation among arm facts before rendering: N is empty; F-I equals F after removing income; all observed non-income facts match exactly. Check rendered F/F-I prompt differences for every request, with explicit handling of missing facts/whitespace. Reject rather than silently overwrite duplicate agents. Hash the validated plan and transmit only its message field. The native runner must preserve this plan and log what was actually sent.

**Verification criterion.** Fixtures with income leakage into N, income retained in F-I, changed employment/parenthood, missing arm records and duplicate agents all fail before any request. Every actual plan record satisfies the exact ablation relation and has a recorded prompt digest. If using only the existing preparer, an end-to-end preparation-to-plan test should demonstrate the same invariants rather than relying solely on a hand-built renderer fixture.

### B11 — New integration requirement, major before collection: array hashes do not verify per-arm response alignment

**Evidence/location.** `paired_evaluation.py:14–20` receives one global row-ID sequence and unkeyed outcome arrays. It checks uniqueness and length of that sequence, then applies X to each array (`31–32`). The design/row hashes describe the assumed alignment; they do not verify model-arm row IDs. There is no enclosed response adapter that joins `(respondent, profile number, arm, rollout)` to the frozen reference. In a synthetic 16-row example, rotating one otherwise correct arm array by four places was accepted and manufactured approximately **600 CAD** signed discrepancy under unchanged row/design hashes.

**Consequence.** Positional arrays are a valid low-level API when their caller satisfies the contract; this is not a numerical error in `evaluate()`. The missing caller is nonetheless a material collection gate. Asynchronous returns, retries, shuffled schedules and A/B profile mappings make encounter order an unsafe join rule. Identical lengths and plausible values will not detect such mistakes.

**Concrete fix.** Build a keyed response-to-design adapter before live collection. Retain the request ID, arm, respondent, profile-number-to-A/B mapping, rollout and attempt identity. Resolve retries under the declared rule, require exactly one final outcome/invalid marker per expected row, and explicitly reindex to frozen design row IDs. Reject duplicates, extra/missing records and unknown keys; preserve both rows as invalid when whole-pair parsing fails. Store a human-outcome hash and contrast hash alongside the existing design/row hashes in the campaign/evaluation receipt.

**Verification criterion.** Arbitrarily shuffled and asynchronously returned responses produce identical scores after keyed alignment. Wrong arm/recipient IDs, duplicate final responses and conflicting retry records fail. Missing or malformed pairs populate the intended two frozen rows with missing actions. A deliberately misordered positional array cannot enter the public analysis path without a validated keyed conversion.

### B12 — Still open, major collection/scientific gate: practical ambiguity and one-rollout stability

**Evidence/location.** `protocol.md:90–93,111–115,135–137,147–157,182–188`; aggregate failure receipt. The new protocol explicitly acknowledges these omissions.

**Consequence.** The continuous finite score is valid without a substantive pass/fail threshold. But a campaign can still spend its budget obtaining a score whose sign is driven by one set of stochastic generations or whose completion interval includes opposite scientific conclusions. The preflight receipt demonstrates this risk; it does not measure the probability that a specific model will exhibit it. A pilot with 95% valid replies would be especially insufficient given the failure-weight scenarios. Choosing a resource prefix also changes the exact benchmark; it is not simply increasing precision for one unchanged finite target.

**Concrete fix.** Before main generation, freeze the chosen cohort/tier, model/settings, cost cap, repeated-generation diagnostic allocation, common-task audit and presentation sensitivity. State the scientific question the continuous scores will answer and how ambiguous or unstable outcomes will be reported. A substantive margin is needed for claims of acceptable or meaningfully better fidelity; it is not needed merely to publish the CAD score. If expected-response or population claims are desired, introduce a separately validated design rather than attach inference to the current score. Set any campaign continuation rule without tuning to whether F is closer to humans.

**Verification criterion.** A frozen campaign manifest and dry-run logs establish the isolation, joins, accounting and retry behavior. Pilot diagnostics report validity and missing contrast weight by arm/group, with repeat-generation and presentation sensitivity evaluated under their declared limited scope. The plan commits to publishing inconclusive bounds and unstable scores. A useful main empirical result must then demonstrate an interpretation that survives its reported completion ranges and is appropriately limited by repeat/presentation diagnostics.

### B13 — Low-priority diagnostic clarification: “random failure” is one scenario, not an estimated distribution

**Evidence/location.** `failure_budget.py:22–31` uses one seeded random subset per fraction. Highest-leverage pair selection is the correct maximum-width choice for a fixed number of failed pairs under the declared reconstructed pairing.

**Consequence.** The seeded random number is reproducible but should not be read as expected or typical width, nor as a coverage statement. No such stronger claim is made explicitly, so this is a labelling/diagnostic improvement rather than a validity failure.

**Concrete fix.** Label it “one seeded random-failure scenario,” or add the exact uniform-subset expected width, `(invalid_pairs / pairs_per_arm) * 4000 * total_absolute_contrast_weight`, optionally accompanied by a distribution from additional draws. Keep the worst-case scenario and realized campaign failure weight prominent.

**Verification criterion.** A synthetic balanced fixture reproduces the analytic expectation and exact highest-leverage width. Labels distinguish design scenarios from empirical model failures and from confidence intervals.
